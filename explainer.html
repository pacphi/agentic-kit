WHYThe story behind the toolbox

Great tools drift. Trust shouldn’t.

You wire up an AI agent stack — persistent memory, security checks, background workers — and it works. Then an upgrade lands. A capability quietly stops working while the CLI still prints “OK.”

That gap between what a tool reports and what it actually does is why agentic-kit exists. The early kit grew around failures encountered while using the stack, with a repair and a check for each boundary it could verify.

The failures that shaped the kit

Memory

“Saved” — but nothing on disk

Native SQLite bindings could disappear after an upgrade while the memory CLI still reported success.

The response: load-test the bindings and confirm a disposable write in the actual database.

Check memory →
Security

A defense layer, silently dead

Ruflo stopped shipping a package that security defend still imported, leaving injection defense broken (#2670).

The response: restore the dependency and exercise the real defense command.

Inspect and repair →
Background work

Workers running beyond the session

Background daemons needed explicit controls over their lifetime and token-spending work.

The response: local-only workers by default, stale-daemon cleanup, and opt-in AI workers.

Find daemon controls →
Two more lessons · status displays and old registrations

A reassuring display can leave things out. Regenerated statuslines did not make capability state clear. The kit adds source-specific presence and metric checks, including missing or degraded states where available. That footer still cannot prove every capability is active.

An old registration can outlive its transport. Retired codex mcp-server entries could remain at user or project scope. ak host align previews scoped corrections with recovery backups, preserving supported Ruflo workers and AQE provider routing. See the host realignment decision.

The original shell-kit background records the earlier investigations; troubleshooting connects symptoms to current repairs.

Upstream ships fast, and that’s good. This kit’s job is the gap: detect the drift, converge to a healthy state, and prove it — never assume it.

01Field guide

How do I get set up?

Install the kit, run setup, and open your dashboard. Claude Code is the default host; you can add Codex or OpenCode when you need them.

Installs tools and changes managed configuration
First setup 
npm install -g @pacphi/agentic-kit@next
ak setup
ak status
ak dashboard

What to expect: Setup walks through the selected tools and permissions. Status reports subsystem evidence; the dashboard opens in your browser. Host authentication is a separate step.

Use a maintained Node release supported above, plus npm. The @next channel carries the 4.0 alpha. To inspect setup before applying it, run ak setup --dry-run.

More control · scope, hosts, and optional tools
Choose what setup touches
Machine scope installs global tools; user scope manages guidance and integrations. Project setup also runs when .git exists in the current directory. Use --minimal to skip project setup, or --project to request it without .git.
Add a host
ak setup --codex enables Codex; --opencode enables OpenCode. --primary-host codex also enables Codex and makes it the routing lead.
Review or repeat choices
--reconfigure revisits saved choices. --yes accepts prompts noninteractively, including the disclosed setup trust manifest.
Trim the installation
--no-aqe, --no-ruvnet-brain, and --no-agent-browser skip those integrations. --no-security skips security-surface verification.
Select AQE embeddings
--aqe-embedding-mode local selects the new-setup default: native Ollama with a small embedding model. Install and start Ollama first. Other modes are endpoint, in-process, and unmanaged; use --aqe-embedding-endpoint URL for an existing compatible service. See backend prerequisites.
Opt in to déjà-vu
--with-deja-vu --deja-vu-mode mcp adds the companion and one bounded index pass. Mode auto additionally consents to automatic recalls. It is disabled by default.

Project initialization runs upstream initializers. Review the setup contract for configuration ownership and preservation boundaries.

What’s in the box?

Ruflo supplies orchestration and memory. Agentic QE supplies quality-engineering tools. RuvNet Brain supplies a source-cited knowledge base. Your enabled hosts run coding sessions.

The kit manages their integration and adds status, repair commands, usage evidence, and a local dashboard. Run ak about for the component directory.

02Field guide

Is everything working?

Start with the status report. If something needs a closer look, choose a focused verification suite.

Status inspects · verification runs live checks
Check health 
ak status
ak x verify memory

What to expect: Status shows subsystem observations and suggested repairs. The memory suite exercises storage in a temporary directory. A passing suite proves its checked behavior, not every capability of the stack.

More control · deeper checks and machine-readable results
  • ak alone shows status plus a suggested next action.
  • ak status --deep runs slower probes that launch installed CLIs; --json emits the report for scripts.
  • ak x verify runs all suites. Choose learning, memory, security, aqe, mcp, providers, harvest, or deja-vu to narrow it. These are live operations, not just file-presence checks.
  • ak x aqe-embedding status inspects backend intent; ak x aqe-embedding verify runs a synthetic backend proof without downloading models or writing to your corpus.
How should I read the result?

Installed, configured, and successfully checked are different kinds of evidence. Read the detail beside a status label. Missing evidence is not a measured zero, and provider configuration alone does not establish a working connection.

When a check fails, follow its suggested action or move to repair. Re-run the relevant check afterward.

03Field guide

Something changed.
How do I fix it?

Preview the convergence plan first. Then repair the selected configuration, with or without upgrading packages.

First command previews · second applies repairs
Preview, then repair 
ak sync --dry-run
ak sync --no-upgrade

What to expect: The preview describes planned changes. The second command heals without upgrading Ruflo, AQE, or the kit. Plain ak sync also upgrades before healing and verifying.

More control · inspect and repair one finding

Use Maintenance when you need to understand a specific resource rather than run the broader sync workflow.

ak maintain inventory
ak maintain guidance
ak maintain plan --placement PLACEMENT_ID --executable --json

Copy the real placement ID from inventory. The executable plan records one exact action. Inspect it before applying:

ak maintain apply --plan PLAN_ID --digest SHA256 --actions ACTION_ID --yes
ak maintain receipt --receipt RECEIPT_ID

The uppercase values are placeholders from your output. Applying requires the matching plan, digest, action, and confirmation. ak maintain undo --receipt RECEIPT_ID --yes requests guarded rollback where supported.

For interrupted work, ak maintain audit --receipts RECEIPT_ID inspects the evidence. Recording an outcome is a separate reconcile operation. recover is a read-only audit alias, not an automatic repair.

scan --deep refreshes measurements; discovery and sources manage where inventory looks. See the maintenance guide for scans, recipes, and recovery limits.

More control · hooks, guidance, and host alignment

ak audit hooks --host all inventories hooks without running them. ak heal hooks --host all previews supported repairs. Applying requires exact action IDs and the displayed digest:

ak heal hooks --action ACTION_ID --plan-digest SHA --apply --yes

Use --undo RECEIPT_ID or --recover RECEIPT_ID to preview rollback or interrupted-transaction recovery; add --apply --yes to perform it. Trust and consent remain user-owned.

ak x reference diff previews managed guidance drift; ak x reference sync reconciles it. ak host align previews transport problems; --apply offers backed-up correction. Host alignment has recovery backups, but not automatic dashboard Undo for its repair recipe.

04Field guide

How do I choose
who does the work?

A host is the coding CLI running a session. A provider serves the model behind it. Choose your hosts, then route each activity to the host you want.

These examples inspect and preview only
Inspect a pipeline 
ak host status
ak run feature "add rate limiting" --dry-run

What to expect: The plan shows the workers and their routes before execution. Templates include feature, security, refactor, packaging, and release.

More control · saved choices versus one-run overrides
Enable your desired hosts
ak host pick --host claude,codex saves the complete enabled set. Leaving a previously enabled host out disables its managed wiring. OpenCode can join the set and accept explicit activity routes, but cannot be primary.
Save a routing preference
ak host pick --route 'testing:codex' persists a route; sync preserves user choices. --primary-host claude|codex selects the routing lead.
Try a route for one run
ak run feature "add rate limiting" --route 'testing:codex' --dry-run previews a temporary override. The format is activity:host[:model]; repeat the flag for more activities.
Refresh seeded defaults
ak host refresh --activity architecture,design updates selected seeded routes without replacing user pins. Sync does not do this automatically.
Choose providers separately
ak host pick also offers --aqe-provider, --aqe-fallback, and --provider. Host diversity does not necessarily mean provider diversity. See provider setup and authentication.
More control · run with explicit limits

Remove --dry-run when you are ready to execute. Workers use your CLI trust settings in the target repository.

ak run feature "add rate limiting" --max-concurrent 2 --timeout 120000
  • --max-concurrent bounds simultaneous workers (default 4).
  • --timeout is in milliseconds: 120000 is two minutes, the default budget per attempt. Teardown is separately bounded.
  • --escalate enables bounded retry through configured escalation ladders. Permission, consent, and uncertain outcomes are not escalated.
  • --json emits a machine-readable plan or result.

05Field guide

Where are my tokens going?

Look at local session usage and repeated prompt patterns. Then inspect startup context or model choices if you need a closer explanation.

Reads local transcript evidence · no provider request
Inspect usage 
ak usage score --window 30
ak usage prompts --window 30

What to expect: A usage summary and deterministic prompt-pattern findings. API-equivalent estimates are separate from what your subscription actually bills.

More control · windows, prompt text, and account analytics
  • score --window accepts 7, 14, or 30 days; the default is 14. prompts --window also accepts all, its default.
  • --json emits structured results.
  • Prompt text is opt-in. Normal prompt reports use stored fingerprints. ak usage prompts --deep re-reads transcripts and prints verbatim examples. With --json, that text is in the payload too; redirect only if you intend to save it.
  • ak usage status inspects the separate provider-account cache. ak usage refresh openrouter explicitly fetches account metadata and requires OPENROUTER_MANAGEMENT_KEY, not an inference key. Use --dry-run to preview.
Why is so much context used before I start?

ak audit context --host all measures startup guidance and bounded skill/MCP metadata, model-window facts, and static hook counts. It does not execute hooks or expose raw content. Add --project PATH or --all-projects to expand the audit scope.

ak x skills plan inspects project skill evidence without changing it. ak x codex-context status shows Codex capacity settings; max --dry-run previews an opt-in maximum request from its native model catalog. Applying requires a new Codex session to take effect.

Has my model changed, and should I switch?

Start with ak models status. ak models refresh --all refreshes evidence from named local/configured sources; --online additionally permits an OpenCode catalog refresh. Other model commands read the local snapshot cache.

  • ak models diff compares snapshots.
  • ak models explain HOST:MODEL explains one model’s evidence.
  • ak models plan --activity testing --to HOST:MODEL previews a switch’s routing impact. Replace HOST:MODEL with an available model from your inventory.

A model plan does not change routing. Apply a choice through ak host pick --route after reviewing it. See the model guide.

06Field guide

How do I inspect
or share the evidence?

Open the local dashboard for a readable view, or inspect your machine’s footprint from the terminal. Fleet exports let you combine evidence across installations.

Dashboard serves locally · deep scans and exports write local data
Open the evidence 
ak dashboard
# In another terminal while the dashboard is running:
ak system

What to expect: The dashboard covers About, Overview, Usage, Observability, and System. The footprint report combines current observations with dated results from the last deep scan.

More control · dashboard and fresh measurements

ak dashboard --port 8080 --no-open selects a port and prints the URL without opening a browser. The server runs in the foreground; Ctrl-C stops it. Protect the token-bearing launch URL.

ak system --deep remeasures installation trees, storage, catalog, and projects, then saves the result. It can take minutes on a large machine. Add --json for structured output.

The dashboard binds to localhost. Server-side version checks may contact version services and update caches; guarded Maintenance actions can change managed state. ak admin is a separate maintainer app, default port 7432, with GitHub/npm access.

How do I combine evidence from several installations?

Export a snapshot on each installation, then validate and aggregate the files where you collect them:

ak telemetry export --days 30 --output machine-a.json
ak telemetry validate machine-a.json
ak telemetry aggregate machine-a.json machine-b.json --output fleet.json

machine-b.json must come from the other installation. Output paths must be new files. Export creates a private installation identity on first use and refreshes the local usage index; it does not upload data or start a maintenance scan.

Snapshots exclude raw transcripts, private paths, hostnames, commands, secrets, and configuration. Aggregation selects the newest snapshot per installation with matching lookbacks. Do not add rolling snapshots together.

--days accepts 1–365 (default 30). Aggregate supports --as-of and --stale-after; stale data stays included and flagged. ak telemetry schema and ak telemetry metrics describe the contract. See export boundaries and aggregation rules.

How do I remove it?

Preview the scope before removing the kit’s managed footprint.

Preview removal 
ak uninstall --dry-run

Plain ak uninstall removes the kit’s machine footprint; global Ruflo and AQE packages stay by default. Each removal is confirmed unless you pass --yes.

More control · project and package removal

--this-project also removes this project’s patches. --purge includes Ruflo, AQE, and receipt-owned agent-browser removal, while preserving browser/session/profile data and the déjà-vu package/data.

Déjà-vu removal is separate: --remove-deja-vu removes its Kit-owned package; --purge-deja-vu-data deletes only its derived index. Consult ak uninstall --help and preview your selected flags together.
